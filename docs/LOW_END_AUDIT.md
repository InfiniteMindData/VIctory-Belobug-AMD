# Low-end AMD architecture and performance audit

**Target:** Radeon RX 6400 4 GB, Ryzen 5 5600G, 16 GB system RAM, Windows x64. **Status:** target boot, image correctness, memory peaks and frame times are unmeasured. The first milestone is to reach the same outdoor checkpoint three times with a correct picture and enough memory for the next scene transition. Frame-rate tuning comes after that.

The fork reports about 30 GB private memory and 10.5 GB VRAM on an i9-12900K, 64 GB RAM and RX 7900 XTX. It also reports about 40 ms on the submit thread in a city scene. Those observations make a capacity audit urgent and identify a place to profile. They do not establish an RX 6400 memory minimum, startup result or frame rate. Source links below pin the audited `a-publier` revision, `4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c`. [Upstream machine, scenes and results](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/README.md#L23-L52)

## Where the target differs

The RX 6400 has 12 RDNA 2 compute units, a 64-bit GDDR6 interface, 16 MB Infinity Cache and up to 128 GB/s **on the card**. The card's PCIe interface has four lanes. The 5600G has six cores, 12 threads, integrated graphics and PCIe 3.0. At Gen3 ×4 the encoding-limited ceiling in one direction is roughly 3.94 GB/s before protocol overhead (8 GT/s × 128/130 × 4 ÷ 8). Measure the negotiated link under load. GPU reads from system-memory buffers, uploads, readbacks and migration can compete for that link. A high-end GPU run cannot establish which of these dominates here. [AMD GPU specifications](https://www.amd.com/en/products/graphics/desktops/radeon/6000-series/amd-radeon-rx-6400.html) · [Board interface](https://www.sapphiretech.com/en/news/pulse-6400) · [AMD CPU specifications](https://www.amd.com/en/support/downloads/drivers.html/processors/ryzen/ryzen-5000-series/amd-ryzen-5-5600g.html)

The title runs native x86-64 code. Its D3D12.X calls and CPU-addressable GPU resources enter the HLE and GPU crates. VIctory records or translates list operations, prepares host resources and descriptors, submits host D3D12 work and merges GPU writes needed by title code. Verify AVX2, the actual discrete adapter, SM 6.6, directly indexed heaps and mesh support before interpreting missing draws. The explicit adapter-name path selects by name. The renderer separately checks features and can refuse a pipeline. Preserve those checks and RT-off behavior. [Device boundary](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-hle/src/modules/d3d12x.rs#L12-L25) · [CPU check](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/apps/victory/src/run.rs#L20-L56) · [Adapter selection](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-shader/src/emit/host.rs#L108-L154) · [Device identity and runtime diagnostics](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/host.rs#L1080-L1104) · [Mesh and shader-model checks](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/host.rs#L4167-L4199) · [Pipeline refusal](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/pipeline/host.rs#L449-L456)

## Transfers, submission and pipeline compilation

**Unified memory on a discrete GPU.** Small or ineligible buffers can remain in CPU-accessible memory and incur GPU bus reads. Eligible buffers can have a CPU staging side, a card-local side, and a previous-value buffer used to identify GPU writes. VIctory refreshes modified ranges, compares 64 KiB pieces on the GPU and fetches changed pieces. Narrow writes and aliased title views make order significant. Physics also reads certain GPU-written textures back into title memory. Removing this path has previously caused boats to sink. Distinguish copies entirely inside VRAM, logical payload submitted to copy operations, GPU reads over PCIe, and WDDM migrations. Existing up/fetched counters cover instrumented shadow ranges. They do not measure physical link saturation. Correlate them with queue timing and a short GPUView/PIX trace of paging, CPU waits and DMA packets. [Mirror and compare](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/shadow.rs#L133-L163) · [CPU-accessible heap](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/host.rs#L10113-L10139) · [Transfer counter scope](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/host/traffic.rs#L23-L61) · [Readback and allocation revalidation](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/texback.rs#L127-L246) · [Physics and publication regressions](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/docs/findings.md#L48-L57)

**Submission has a serial section.** Thin list recording can distribute translation across eight workers. The submit lane bounds outstanding work, but `Host::submit` still holds the submission mutex while it resolves shared snapshots, refreshes and dependencies. It can wait for prior GPU writes and also runs the resource sweep. Under pressure, the sweep can scan all eligible textures and sort by age. The source times the latter loop after collecting and sorting candidates, so its reported sweep time can omit that preparation. Inspect a timeline around a long frame before moving or parallelizing work. Count elapsed time on the critical thread separately from summed CPU time on workers and GPU timestamp spans. [List workers](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/list/thin.rs#L303-L332) · [Queue depth and prerequisites](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/queue/behind.rs#L711-L763) · [Submit lock, dependency waits and sweep](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/host.rs#L5711-L5796) · [Candidate sort before timer](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/resource.rs#L2147-L2179) · [CPU and GPU timeline](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/timeline.rs#L1-L21)

**Shader translation and driver compilation are separate costs.** The runtime parses console containers, translates programs and uses a versioned DXIL cache keyed by translation settings. A translation hit can still require a driver PSO for a particular root signature, shader set and render state. A rejected pipeline library falls back to an empty one. With 12 logical processors available, default policy selects eight ordinary PSO workers plus two screen workers when enabled. The normal per-frame wait budget is 500 ms, and screen work can wait up to 10 s. Missing an available PSO can omit a draw. Compare translation hits/misses, pending PSOs, dropped draws and actual frame intervals on cold and warm runs. The `victory warm --used` input comes from previous runs. A global reduction in wait time can improve the graph by dropping work. ## Resolution and FSR

Series S is a title-selected profile. In the Series X native upscaler, the documented default internal scale is 2/3 per axis. An accepted 1920×1080 output can therefore mean a 1280×720 scene. Reducing dimensions to 2/3 gives 4/9 as many scene pixels. Fixed-size heaps, title allocations, texture residency and submission overhead do not scale by that ratio. Verify the title patch result and actual scene target, swap chain and HUD dimensions in a separate diagnostic capture. Window size alone is insufficient. [Output and scale paths](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-loader/src/resolution.rs#L14-L39), [Patch-result logging](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-loader/src/resolution.rs#L294-L325)

The PC temporal bridge currently targets a verified retail build, Series X, 3840×2160 SDR. Quality, balanced and performance request 2560×1440, 2258×1270 and 1920×1080 input. It selects FSR 4.1.2 if the supplied SDK offers it for the adapter, otherwise the highest available 3.1 provider, and reports failure if neither is available. The provider needs valid color, depth, motion and output resources plus jitter, motion scaling, dimensions and reset state. The runtime logs actual sizes on the first successful dispatch. The separate Series S `VICTORY_FFX_SCALE=0.5` experiment has a documented zero-jitter-phase crash. There is no verified PC FSR-to-1080p profile here. Qualify a lower-output bridge only after native 1080p measurements identify pixel or target-memory cost, with tests for motion, disocclusion, menus, resize and a camera cut. ## Baseline on Windows

Use the pinned toolchain and an owned, identified title build. Store captures, caches and saves outside the checkout. Run from the repository root with a configured `victory.toml`. Use the same Windows build, driver, power settings, display mode, camera path and save across comparisons. Record adapter name and PCI IDs from the log, negotiated PCIe width/speed under load, usable RAM, page-file mode/limit, build SHA, title build/hash and cache state with each run.

The first reference uses the fork's normal launcher with RT off, Series X and its stock output. The only overrides select the measured adapter and diagnostics. It enables light DRED, thin lists, eight joined parts, upload ahead, show-after and the keep-awake compute workload. `-Safe` is a different configuration. The launcher clears most inherited switches. Pass each experiment through `-More`. $LASTEXITCODE | Out-File (Join-Path $run 'exit-code.txt')

1. **Separate startup, first world entry and steady state.** Record wall-clock times for launch, first accepted present, controllable checkpoint, outdoor traversal, return to the start, and exit/failure. Use the same save and repeatable 120-second route for three warm runs per configuration, alternating control and candidate. Keep loading and menus out of gameplay percentiles. If boot fails, retain the last complete CSV row, exit code, DRED/crash log and last visible checkpoint. Report the failure stage and time to failure.
2. **Control caches.** For an application-cold run, point `VICTORY_CACHE_DIR` to a fresh sibling folder. Keep the same save separately. Record the driver-cache state as warm, cold or unknown. Reuse the application cache for warm traversal. To test offline warmup, run the same binary and adapter with `victory shaders <archives>` and, after a discovery run, `victory warm --used`. Record which stage was warmed. Do not pool cold runs with warm runs.
3. **Measure per-frame intervals.** In a second terminal at the route start, point `$run` at that run's folder and use a recent PresentMon console release. Filter the output to the title PID and main swap chain. Keep dropped presents in the raw data. Sort valid `MsBetweenPresents` intervals within the route and use nearest-rank p50/p95/p99. Report valid frame count, max and fraction over 50/100 ms. Also inspect display intervals/drops for a smooth-presenting but visibly frozen scene. [PresentMon command and CSV definitions](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md)

```powershell
PresentMon.exe --process_name victory.exe --v1_metrics --timed 120 --terminate_after_timed --output_file "$run\presents.csv"
```

4. **Read pressure and work together.** The new diagnostics-only `VICTORY_BASELINE_DIR` sampler runs after CPU preflight and before loading the executable. It immediately starts a background capture, sleeps one second after each sample, uses the device's adapter LUID and writes one flushed CSV row per sample to `baseline-<pid>.csv`. Create a fresh directory for each run. Blank means unavailable (including a busy pool or an uninitialized GPU). A zero is a successful observation. The file contains numeric counters only. | CSV fields | How to use them |
| --- | --- |
| `elapsed_ms`, `unix_ms`, `title_presents_total` | Align phase markers by time, use measured sample spacing for rates. A flat present count during a stall is valid. Title calls can precede an accepted DXGI present. Percentiles require the per-present capture. |
| `local_usage_bytes`, `local_budget_bytes`, nonlocal equivalents | Report peak sampled usage, minimum paired headroom and time above budget using consecutive valid samples. Skip missing or zero budgets for ratios and report coverage. Nonlocal usage can include intentionally shared resources. Confirm paging with ETW. |
| `working_set_bytes`, `private_commit_bytes`, `available_physical_bytes`, `available_commit_bytes` | Report sampled peak working set/private commit and minimum available RAM/commit. Track sustained loss of headroom on repeated traversal. A one-second sample can miss a short peak. |
| Host/title-filled textures, texture pool/empty heaps, list scratch/spare scratch, live staging | These are gauges. Filled textures are included in host textures, empty heaps in pool capacity and spare scratch in scratch. The pool contains backing for placed textures. Compare each series separately. |
| Evicted/recreated bytes and no-room passes (`_total`), slots waiting | Take end-minus-start for cumulative counters within one PID. Waiting is the last sampled heap-pass census, not a global texture inventory. Recreation counts allocation bytes and does not imply an equal PCIe transfer. |
| Shader cache hits/misses (`_total`), pending pipelines | Attribute newly translated entries to cache activity. Compare against driver-library hits, PSO waits and dropped draws in the log. Sampled queue depth can miss short compiles. |

Use the existing `ms/frame` line for CPU preparation and copy-back. Its “on the GPU” field derives from **wait time**. Use GPU timestamps or a GPU trace for execution time. In a separate attribution run, `VICTORY_MEMORY_CATEGORIES=1` adds overlapping categories. `VICTORY_MEMORY_MAP=1` walks the virtual address space on every memory report and can stall the submitter. Keep it off in timing runs. Separate measurement runs from intrusive captures, especially in the world where the upstream README reports a watchdog exit during frame recording. ## Experiments and implementation order

Use one change per paired comparison. All thresholds below are proposed decision criteria. A missing counter or a run that never reaches the checkpoint leaves the corresponding decision open.

| Priority | Condition and experiment | Proposed change, acceptance and risk |
| --- | --- | --- |
| P0 · establish feasibility | Record the reference above. If it fails before world entry, first try `VICTORY_OUTPUT=1920x1080` with the rest of the launcher identical. Test Series S as its own configuration. For a matched S/X pair, reuse the launcher's environment in that PowerShell session and invoke `target\diag\victory.exe run $exe --execute --console series-s` directly with a fresh capture directory and log, then repeat with `series-x`. Use the same output policy in both. | Record 3/3 successful boots and 3/3 completed routes before claiming feasibility. A failure with a populated CSV is still a valid baseline. Compare sampler on/off at the same checkpoint with external PresentMon on both. Investigate a repeatable p95 shift above 5%. |
| P1 · VRAM admission and empty heaps | If the waiting count and no-room passes rise while wholly empty heaps occupy substantial budget, compare `VICTORY_RESIDENCY=1` with stock. Check empty stock, target bursts, re-creation and long mapping waits. Only if headroom accounting is implicated, prototype scaling speculative stock or the target allowance to observed budget and actual transition demand. | On each run require at least a 10% reduction in sampled peak local usage **or** a 20% reduction in no-room passes per second, with no new missing textures, a stable or better p90 written-to-shown latency bucket, and no increase in time over local budget. [Texture latency buckets](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/texlate.rs#L105-L128) Preserve mandatory target creation, ownership checks, delayed reuse and publication fences. |
| P1 · host memory | If private commit climbs or free RAM/commit crosses the existing 3/4 GiB pressure thresholds, inspect list allocation, scratch, staging and overlapping window spans. Residency can limit speculative prefetch to 64 MiB or 16 MiB under critical commit. A 4 GB budget selects a 96 MiB base allowance. At 1,024 due slots, catch-up can triple the byte and time limits before the pressure clamp. Required bakes and an explicit stage-MiB override skip that clamp. [Catch-up, overrides and admission order](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/draw.rs#L2376-L2418) Test `VICTORY_WINDOW_BUDGET_MB` only if unreferenced windows dominate. [Staging reserve](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/residency.rs#L71-L115), [pressure/admission](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/residency.rs#L117-L193) · [Application of stage limits](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/draw.rs#L2266-L2305), [tier sizes](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/draw.rs#L4698-L4706) · [Eligible window reclaim](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/shadow.rs#L3004-L3056) | First target a ≥10% reduction in peak private commit from the identified category. Require ≥1 GiB available physical memory and ≥1 GiB available commit at all valid samples on a 15-minute loop, with zero OOM/device removals. A larger page file may allow commitment while paging still destroys frame time. Reclaimed windows can increase copies on the next lap. |
| P2 · transfer versus submission | If up/fetched payload and waits track the spikes, attribute the highest-traffic spans and test one existing port: `VICTORY_PORT_CONSTANTS` for its mapped heap, `VICTORY_PORT_CBV` for CBV fills, or `VICTORY_PORT_DESCRIPTORS` for scanning. If the GPU queue is idle while preparation is late, profile `VICTORY_THIN_THREADS`, `VICTORY_PORT_GUARD` or `VICTORY_PORT_JOURNAL` separately. Check actual activation, fallback and build-specific patch counts. [Mapped constants](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/port.rs#L71-L82) · [CBV path](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/port_cbv.rs#L1-L46) · [Descriptor hook result](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/port_descriptors.rs#L534-L567) · [Journal](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/watch.rs#L421-L475), [guard](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/watch.rs#L1458-L1506) | Retain a candidate only if its attributable transfer bytes or prepare time falls ≥10% and route p95 improves ≥5% across paired medians. Drawing from a system-memory heap can exchange the saved upload for repeated GPU PCIe reads. Preserve alias coherence, barriers, readback, fences and ordering across overlapping submissions. |
| P2 · cold PSOs and worker contention | If cold stutters coincide with cache activity or PSOs pending, compare offline warmup, then a lower `VICTORY_PIPELINE_WORKERS` count against the measured default. Test `VICTORY_CARD_AWAKE=0` separately if aggregate GPU utilization stays high between submits: the launcher enables a persistent compute workload. [Keep-awake load](https://github.com/InfiniteMindData/VIctory-Belobug-AMD/blob/4eb6cfdf9e61cb112f1f811344ec0dd309eddd6c/crates/victory-gpu/src/host/awake.rs#L1-L25) | Seek ≥20% fewer intervals above 100 ms in the same cache class. Require equal or fewer dropped draws and equal first-scene coverage. Check first screen-pass latency and time to gameplay. An idle GPU with a full CPU queue calls for a different fix from a saturated GPU. |
| P3 · resolution / FSR | If GPU timestamps or render-target growth dominate, compare validated Series X output modes (1080p then 720p), then internal scale at fixed output. Test the unmodified title scaler first. A separate PC temporal profile would need verified title sites, input/output resource dimensions, provider selection and a fallback. | Require ≥10% lower GPU frame time or target bytes at fixed scene and an improved p95 relative to the matched native control. Compare HUD/text at output resolution, depth edges, moving foliage, exposure and camera resets. Report the image-quality tradeoff. An upscale that leaves CPU stalls or mandatory resources untouched cannot establish low-end feasibility. |

For any candidate default, rerun a ≥12 GB GPU with the original high-end settings and three matched runs. Require no new hangs, watchdog exits, device removals, refused PSOs or missing draws. Compare static HUD, materials, depth/shadows and the water/boat and indoor/outdoor transitions against the same-build control. Use deterministic pixel comparisons where available and side-by-side matched frames for temporal effects. Reject repeatable p95 regressions above 5% or peak memory growth above 5% on the control GPU. As a later playability target, use warm outdoor median ≤33.3 ms and p95 ≤50 ms for the full route. None of these gates has been demonstrated on the RX 6400.
